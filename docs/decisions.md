# Decisions

Why the design system is built the way it is, and what was looked at before deciding. The direction itself, the ghost, the terminal, Rosé Pine and the two faces, was settled before this repository existed. This is about how it is built.

## One package

Everything ships as one package, `@whatsaaaa/design-system`, with one entry per part, as the `exports` of `package.json` list them.

Several packages, one per part, is how large systems do it (Primer has primitives, CSS and components apart). It pays when parts have their own users and their own release rhythm. Here every part reads the same tokens, changes together and has one maintainer, so one version and one install is simpler and cannot drift. `@vue/theme`, Open Props and VoidZero's shared docs theme are single packages for the same reason. Every peer is optional, so a project that only wants the styles installs nothing extra.

## Tokens: the DTCG format, built by Terrazzo

The tokens are written in the Design Tokens Community Group format (the 2025.10 version, with a resolver file for the two themes) and built by [Terrazzo](https://terrazzo.app).

| Option                                                                              | What it is                                                | Why or why not                                                                                                                                                                                                                                    |
| ----------------------------------------------------------------------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Terrazzo 2**                                                                      | Built around the DTCG format and its resolver             | Chosen. It reads the current format as it is, emits the theme blocks through plain selectors that this repository controls, and lints the token files. Themes are a resolver with two contexts, which is the standard way to say "dark and light" |
| Style Dictionary 5                                                                  | The long-standing tool, with DTCG support since version 4 | Its own docs say the 2025.10 format is not fully supported yet, and a theme switch needs a custom format                                                                                                                                          |
| Hand-written, as Open Props, Radix Colors, the Rosé Pine and Catppuccin palettes do | A script that turns a JavaScript object into CSS          | The least machinery, but a format of our own. Nothing else could read the tokens                                                                                                                                                                  |

Two things Terrazzo does not do are done here. Its contrast rule only checks the default theme, so the contrast of every pair is a unit test over both themes, driven by `tokens/contrast.json` and by the names of the component tier. And its JavaScript output is the resolver API, which is right for build scripts and is what the package exports as data.

Colors are written as sRGB hex, the exact Rosé Pine values, not converted to another color space, because the contrast figures are measured from those values.

## Themes: an attribute and a media query

Dark is the default block, light applies under `prefers-color-scheme: light`, and `data-theme` overrides both, on the page or on any element inside it. So does a `dark` or `light` class, which Nuxt UI and VueUse's `useColorMode` put on `<html>`, so an app built on them needs no script to bridge the two. The toggle script in Tailwind's docs, VueUse's `useDark` and VitePress mark light only by leaving `dark` off. A stylesheet cannot tell that from no choice at all, so no class stays the system's theme. An app on one of those keeps a `light` class in step with `dark`: on for light, off for dark or the system. The docs theme sets `data-theme` for every choice from VitePress's switch instead. On one element the attribute wins over the class, so `setTheme` still holds where a library has left its class. The selectors of both are made in one place, `scripts/lib/theme-selectors.ts`, and the token build writes them into the theme blocks of the tokens, into the rules of an element for one theme only and into the `dark:` and `light:` variants of the Tailwind entry. A `.dark` block of its own would have needed a copy of every value.

The newer way is `light-dark()` with `color-scheme`. It needs no second block and nests for free. It was not used because a browser without it shows no colors at all, and the selector approach works everywhere and still nests: the samples in the style guide use `data-theme` or a `dark` or `light` class on an element.

An element for one theme only, `ws-theme-dark` or `ws-theme-light`, is hidden by selectors too. A token cannot hide an element: `display` cannot be switched by a variable without losing the display the element has, and a container style query, which could read the theme from a variable, is not in every browser yet. A selector cannot ask for the nearest `data-theme` or class, so the rules spell out the depths that occur: a theme on `<html>` and up to three parts held in a theme, one in the other. They hide with `!important`, so no other rule that sets the display of the element shows it in the wrong theme.

The color of the browser's own bars, `<meta name="theme-color">`, is read from the stylesheet, from `--ws-color-bg` on `<html>`, and not written into the theme module. So it is the token's value in the theme that applies, by the same rules as everything else, and the module carries no copy of a color. The price is that it is known only once the stylesheet is there: the head script sets it in the first animation frame, which a browser runs once the stylesheets of the `<head>` are loaded and before the first paint. Material for MkDocs reads its theme-color from the page the same way.

A page without JavaScript, and a link preview, which reads the HTML as it is sent, would get no color at all that way. So the served `<head>` has two tags of its own: the dark background, and the light one under `media="(prefers-color-scheme: light)"`, which is the theme the stylesheet chooses with no choice by hand. They are written from the tokens when a site is built, by `themeColorMeta` in its own entry, `theme/meta`, which reads the token data: the theme module, which runs in the page, still carries no color. The head script then takes both tags over. The dark one comes first, under `not all and (prefers-color-scheme: light)`, so a reader that takes the first tag and ignores `media` gets the default theme, and a browser that knows `media` gets the same as the stylesheet. One tag without `media` would have left a light system with the dark color until the script ran, and none at all without it.

## Forms: shared measures, not components

The system draws no fields and no buttons. Each app that uses it draws its own from the roles, in a few rules each, and the system gives them what they have to share to look like one family: a control height, the sizes of the small boxes, a hover and a pressed fill, a check icon, and the two pieces that are more than a box, a segmented control and a list of terms and values. A set of field classes would have to cover every state of every control in every framework's markup, which the first three apps did not need. What they share by name beyond the roles is in the component tier, below.

The hover and pressed fills of the interactive color are that color a step further from the page in OKLab lightness, 0.05 and 0.1: lighter on dark, darker on light, so the label on them gains contrast in both themes. The first apps mixed the text color in instead, which barely moves the fill on Dawn, where pine and the text are about as dark.

Icons next to text have one size, `--ws-size-icon`, 16 px. Each is drawn on a grid of 16 in strokes of 1.5, the weight of the text it stands next to. Drawn at another size the stroke scales with it: at 12 px it is just over a pixel and blurs, at 24 px it is heavier than the text beside it. The apps drew every icon at 16 px already, the tick, the icon of a field in error and the calendar of a date picker. The one larger size is `--ws-size-icon-lg`, 20 px, for the icon in a control of the two large sizes, where Nuxt UI draws a larger one too. Any other icon that has to be larger is a drawing of its own. The chevron of a prompt and the arrow of a link are not on the grid: they are glyphs, sized in `em` with their text.

The sections of a review step share their term column through a group around their lists, `ws-pairs-group`, that holds the columns, with each list and each row in it a subgrid of them. So the column is as wide as the longest term of all the sections, measured by the browser, and a section of short terms lines up with the rest. A fixed width for the terms, a variable an app would set, was the alternative: it needs no group, but it is a guess, too wide for short terms and too narrow for a long one in another language. One list with the headings as rows of it was another, but a heading inside a `<dl>` is not a term or a value. A browser without subgrid, Chrome before 117, sizes each list apart, as before.

The pressed segment of a segmented control is raised, with a thicker edge of the interactive color, not filled. A filled segment next to a filled primary button reads as a second primary button. The edge carries the state at 3:1 or more on the page and on the raised fill.

## Component tier: thin, patterns first

The tokens have a third tier next to the palette and the semantic roles and measures: `tokens/components/`, the decisions that every implementation of a control has to make alike. ui-vue draws Nuxt UI's controls, ui-react is to draw shadcn/ui's on Radix, and an app may draw its own. Each reads the tier by name at runtime, `var(--ws-field-border-invalid)`, so a value changed in the system reaches all of them with a release, and each proves in its own tests that it meets the specs. The system still draws no fields and no buttons: it names what they share.

Terrazzo, which builds the tokens, advises against component tokens in its style guide: "limiting your tokens to 2 layers: primitive and semantic will yield dividends in saved time and complexity ... TL;DR don't use component tokens". Wikimedia Codex keeps them for single-use exceptions. Their reason is the cost of a token for every property of every component. The system goes further all the same, because the same field and button are already drawn three times, in ui-vue and in the two form samples, with ui-react to come, and the copies drift: one sample gives a disabled button the hover fill and the other does not. Nathan Curtis promotes a decision to a shared name once three components need it. So the tier is thin, as Primer's `control` pattern and Carbon's few component tokens are, and patterns come first:

- **A pattern before a component.** `control` holds what every one-line control shares, a button, a field, a select's trigger, a segmented control and a link tab: the height, the gap and the icon size of each of Nuxt UI's five sizes, the radius and the border widths. `field` holds the colors of a text field, a select and a select menu, and every field's label, help, error and required mark. `choice` holds what a checkbox and a radio group share: the size and the edge of the box or the circle, the fill and the mark of a checked one, and an option's label and description. `overlay` holds what a select's list and a modal's window share: the surface, the edge and its width, and a radius and a padding for each, the list's and the window's. A group of one component comes with its spec, and holds only what is its own: `tag` holds a badge's colors and paddings, which the system's own `.ws-tag` reads too, so the two cannot drift apart. A card has no group: it is the surface, the border and the large radius, roles its spec names directly.
- **A token earns its name**: a value several controls share, a decision of a state that every implementation has to make alike, or a measure the system lacks. What a spec can name with a semantic token, such as the focus ring, stays one.
- **Every token is an alias of a semantic token**, never a value of its own, a palette color or another tier token, as Material 3 maps each component token to a system token. A value the system lacks becomes a semantic token first: the required mark needed `color.brand-text`, and the sizes other than md needed `size.control-xs` to `size.control-xl` and `size.icon-lg`, and the boxes and ticks of a checkbox `size.check-xs` to `size.check-xl`, `size.tick-sm` and `size.tick-lg`.
- **Names are `<group>.<variant>.<part>.<property>.<state>`**, each segment there only where it varies, the property in the system's words (`bg`, `text`, `border`, `icon`, `height`, `size` for the side of a square part such as a checkbox's box, `padding`, `padding-inline`, `padding-block`, `gap`, `radius`, `border-width`, `icon-size`, `font-weight`, `text-style`) and the state, or for a measure the size, last, from closed lists, in Primer's order: `control.height.md` is `--ws-control-height-md`, `field.border.invalid` is `--ws-field-border-invalid`. With the state last, every state of a property sorts together, and a token cannot also be a group, so a property with states writes `rest` out.

`tests/tier.test.ts` checks what a machine can: every token is an alias of a semantic token, its name follows the grammar, each group is the file of its name and the resolver reads them all, and the tier is declared on every element that can choose a theme. That every tier token is read by a spec, and every spec names tokens that exist, is checked with the specs.

The resolver reads the tier last, after the theme, and the CSS plugin writes it as a block of its own on `:root` and on every element that chooses a theme, with the selectors of `scripts/lib/theme-selectors.ts`. A variable that reads another is read where it is declared: declared on `:root` alone, `--ws-field-bg` would keep the page's theme inside a part held in the other theme, the trap of Tailwind's `@theme` without `inline`. Declared on every element that can choose a theme, it follows the theme in effect and costs one line per token, with no copy per theme. The tier is left out of Tailwind's theme, with a reason for each group generated from the files: an implementation reads it by name, `h-(--ws-control-height-md)`, and a utility of the theme would let any element take a field's color. Its colors need no entries in `tokens/contrast.json`: a name says what is drawn on what, so `scripts/lib/contrast.ts` derives the pairs: text at 4.5 and an icon at 3 on the fill of their state, else the fill at rest, else the page, and an edge at 3 on that fill and on the page, as it lies between the two. A color at rest is read too on the fill of every other state that names no color of its own for it, as a label kept on hover is, so a checked box is measured with its own edge and not with the edge at rest. Disabled is exempt, and the contrast test measures them with the rest.

The values are what ui-vue draws today on Nuxt UI 4.12, measured in its playground, on the system's scales. Nuxt UI's sizes are 24 to 40 px tall, with gaps of 4 to 8 px and icons of 16 to 24 px; ui-vue moves them up so md is the system's control height: 28, 32, 40, 44 and 48 px tall, gaps of 6, 6, 8, 8 and 10 px, icons of 16 px to md and 20 px at lg and xl. Its buttons draw their icons at 14 and 18 px at xs and lg, off the scale; the tier takes its fields' 16 and 20 px. The radius and the border widths are the same at every size, as in Nuxt UI. The required mark is red in both themes. Love reads at 6.07:1 on the dark page but 3.84:1 on Dawn's, under the 4.5:1 of small text, so on light `color.brand-text` is love 0.05 further from the page in OKLab lightness, the step of the interactive hover fill: 4.73:1.

An overlay has no shadow, as nothing in the system does: borders separate things, and the Tailwind entry takes Nuxt UI's shadows away. So the tier has no shadow token, which would have to alias a semantic shadow the system does not have, and the select's and the modal's specs say `box-shadow: none` as a value. Its edge is the field border, not the border of a card or of the frame's window: `color.border` reads at 1.57:1 on the surface in the dark theme and 1.33:1 in the light one, and an edge of the tier has to reach 3:1 on its fill and on the page, as a list that opens over a form and a window over a dimmed page are told apart from what is under them by it. `color.field-border` reads at 3.19:1 and 4.23:1 on the surface, and it is the edge of the select's trigger too, so the list reads as part of the control it hangs from. The window is 32rem wide at most, a value until the system has a measure for windows, and its padding narrows below 64rem as the frame's do.

A tag's edge is not an edge of the tier. The outlined tag draws `color.border`, as a card and the frame's window do, under 3:1 on the page: it frames a word that carries the tag alone, as a card's edge frames its content, and a tag does not lie over anything it has to be told apart from. So the badge and the card specs name `color.border` directly, and the tier's rule that its edges reach 3:1 stays whole. The outlined tag's edge is inside its block padding and outside its inline padding, as `.ws-tag--outline` drew it before the tier: its tokens keep that, so the tag looks as it did.

The table's group, `table`, is read by the prose table too, so the two cannot drift: the head's surface and its secondary text, and the room in each cell. The spec adds a row's text and its fill under the pointer and once chosen. A row under the pointer is raised, as everything under the pointer is, and a chosen row takes the selection color, the background of selected text. ui-vue raises a chosen row and raises a hovered one at half that, which on Dawn differ by 1.05:1, too close to tell apart; raised and the selection color differ by 1.93:1 in the dark theme and 1.15:1 in the light one, and a row's text reads at 4.5:1 or more on both. The frame's edge and the lines between the rows stay `color.border`, named by the spec as a semantic token: an edge of the tier is held to 3:1 by its name, while a table's lines are decorative, its shape carried by its head and its columns, and forced colors keep them as borders. A chosen row takes the selection colors there, as a checked box does.

The tabs have no group. Each state of a tab is a role that already names that use, `color.text-secondary` for idle navigation, `color.text` under the pointer and for the current tab, and `color.brand` for its bar, a marker of where you are, and its height, gap and icon are the control's, so a group would repeat them under other names. Only the frame's look is specced, a row of labels over a line: Nuxt UI's pill tabs, a bar whose current tab is raised, look like the segmented control, which covers that use.

## Component specs: data, and a page drawn from it

A spec is a JSON file, `specs/<component>.spec.json`, checked against `specs/spec.schema.json`, and its page in the style guide is drawn from it, as the color page is drawn from the tokens. A page of prose with a table in it was the alternative: it reads as well, but a test cannot read it, and the page and the implementations would drift apart as the three copies of the field did. So the data is the contract every implementation's parity test reads, published in the package, and the page cannot say something else.

Its state table is the whole mapping, a row for each kind, state, part and CSS property, as Spectrum's design data and Primer's component tokens keep their per-state decisions as data. A row names a component token where every implementation makes a decision of its own, a semantic token where one says it all, such as the focus ring's `color.interactive`, and a value only where the system writes one without a token, such as the ring's `3px` offset or `transparent`. A state lists what it changes from rest, so a row is a fact a test can check, not a default it has to infer. A row may hold for every kind, `*`, or a list of them, and for one size or all of them: written out per kind and size, the button's table would be five times as long and as easy to get wrong. The states are the closed list the tier's names end in, so a spec and a token cannot name one state two ways. The properties are a closed list too, each with the token types it can take, so `height` cannot read a color.

The tests check what a machine can: each spec is valid, names only the kinds, states, parts and sizes it declares, names tokens that exist and fit their property, names each property once for a kind, state, part and size, or twice where one row holds `with` a part drawn and the other `without` it, and has a gallery example of every kind in every state its table names. Every tier token is read by some spec. A spec names Lucide's icons, as the system's set is to be Lucide's.

The button's colors are a group of the tier, `button`, as each kind's fill, edge and label in each state is a decision both implementations have to make alike and that can change on its own. Its measures are the control's, and its paddings and type are semantic tokens that the spec names. The edge of a button and of a field is a border in the spec, not the inset ring ui-vue draws: a border survives forced colors, where a ring, a box shadow, does not. A secondary button keeps its hover edge while it is pressed, as the field border on the raised fill is 2.93:1 in the dark theme, under the 3:1 of an edge. Danger is an outline in both themes: no red of Rosé Pine Dawn carries small light text at 4.5:1, and a fill of the text color, as ui-vue's error buttons have in the light theme, looks like a neutral button.

The checkbox and the radio group share the `choice` group, as their box and circle, edge, fill, mark, label and description are drawn alike and the sample apps draw them as one `.choice__input`. Their sizes are what ui-vue draws on Nuxt UI 4.12, as the control's are: boxes of 14, 16, 20, 22 and 24 px, a tick at the system's icon size in the 20 px box and four fifths of the box at the others, to the even pixel, so it stays centered, and a dot of 6 to 10 px. Only the list look is specced. A card, the whole option as a bordered panel, has the divider color for its edge at rest, under the 3:1 of an edge that shows a state, and a hover fill of the raised color at half, which the system has no token for; it stays an implementation's own until the system decides both. A disabled box that is checked keeps its tick on the faint fill, as the radio does, so a reader sees the answer that cannot be changed.

## Parity helper: computed styles, in each implementation's own gallery

The specs are held in each implementation's repository, by `@whatsaaaa/design-system/testing`, against its own gallery. Images of the Vue and the React gallery compared with each other were the alternative. Their DOM, icons and library internals differ where nothing is wrong, so such a diff would be noise, while what both must share, a spec's values, shows exactly in the computed styles. The helper is the prototype that held ui-vue's button and checkbox to fourteen values, made to read a spec's data, and is tested here against a gallery of plain HTML, so it needs no framework. Playwright is an optional peer, as Tailwind and VitePress are: only this entry imports it.

A token is resolved on a probe inside the part, or next to one that cannot hold an element, so it reads the variables the part reads, and one expectation holds in both themes and in a part of the page held in the other theme. A state that the pointer or the keyboard causes is forced with `data-demo`, as ui-vue's gallery already draws it, since a hover by the pointer holds for one example at a time and the focus for one in the page. A row is checked wherever it holds, and a row that no example draws fails, so an implementation cannot pass a spec by leaving a part out of its gallery. In forced colors an edge is checked by its computed border or outline, and a checked, indeterminate, current or selected example by its image against its example at rest, because the bug the check is for is a state the computed styles still have while nothing on the screen shows it. A checked box's fill and tick are not drawn at rest at all, so there the two examples are compared whole. An image is of the pixels its part covers at least half of, and two images more than a pixel apart in size are not compared: a row at a fraction of a pixel would take in the line under it where the same row at a whole pixel does not, and the bar under the current tab of the example at rest is under another tab, of another width, so either would differ from the other with nothing to tell the two states apart. Where a part is skipped for its size, the two examples are compared whole, so a bar drawn outside its tab's box, as Nuxt UI draws one bar for the row, still tells them apart.

## The frame on a phone: a gutter of 16 px

Below 64rem one length, `--ws-space-16`, is the gutter: the brand of the tab bar starts that far in from the window's edge, and the content under it, a pane, a page or a form, is padded by the same, so the two start at one pixel. The style guide's example padded a pane 20 px, which left it 4 px off the brand, and the apps each chose for themselves. 16 px was chosen over 20 because the brand already had it, the form example and the apps used it, and on a 320 px phone the four pixels a side go to the content. The docs theme takes it on a phone too, below 48rem, where the default theme lays out for one: it padded the brand 16 px and the page and the row of its menu 24 px. From 48rem the default theme centers the page, which then shares no edge with the brand.

The status line pads its items 10 px below 64rem, and 14 px from there up. At 390 px, with the mode, the keys switch and the theme button, 14 px left the path a few characters. The website set 10 px on a phone for that reason, and with it the path keeps about 32 px more. Every item takes the smaller padding, not only the path, so the items still look alike.

The path shows only with room for five characters and the ellipsis, `6ch` of the status line's mono face, and goes as a whole with less. With 10 px the path got the room for a letter and the ellipsis where it had gone before, `w…` on a 320 px phone, which reads as a glitch and not as a path cut on purpose. Five characters are a short word or the start of one, such as `~/pro…` or `docs/…`. Fewer leave a stub. The width is in `ch` of the line's own face, not a length from the spacing scale, so it holds characters at any font size. It is written out in the container query, next to the padding, as a query takes no `var()`.

## Breakpoints: 64rem and 40rem

The system has two widths where a layout changes, and no scale of them. Below 64rem, `--ws-compact`, a page has one column. Below 40rem, `--ws-narrow`, a row of fields stacks. The first apps had only the first, so a tablet showed one field to a line in a column that had room for two: a field such as a name or a date reads well from about 17rem, and two with the gap between them and the gutters of the page fit in about 38rem.

40rem is Tailwind's `sm`, as 64rem is its `lg`, so the Tailwind entry needs no breakpoints of its own: `max-sm:` and `max-lg:` are the system's two. The name says what the width is, narrow, as compact does, and not a device. A third width, such as Tailwind's `md` at 48rem, was left out: each is a layout to design and to check, and no app needed one.

## Tailwind entry: plain CSS, with an entry for Tailwind CSS v4

The stylesheets stay plain CSS, which any page can import, and an app on Tailwind CSS v4 imports `tailwind.css` in their place: Tailwind and the same stylesheets in Tailwind's cascade layers, with the tokens as its theme. Rewriting the system in Tailwind, as utilities and `@apply`, was the alternative. It would make Tailwind a dependency of everything that uses the system, the docs theme and the framework-free pages included, for what one entry already gives the apps on it. Tailwind stays an optional peer, and only that entry needs it.

The theme is `@theme inline`, so a utility reads the token where it is used: `bg-surface` is `background-color: var(--ws-color-surface)`. Without `inline`, Tailwind declares a variable of its own, `--color-surface`, on `:root`, and the utility reads that. It takes the token's value once, at the root, so the utility keeps the theme of the page and ignores a `data-theme` or a `dark` or `light` class on a part of it. Inline, a utility follows the theme as the system's classes do.

Tailwind's defaults that no token stands behind are taken out: its palette, its shadows, and the families, weights and radii the system does not have. As a class one makes nothing, and in `@apply` one fails the build, so an app does not reach for a color or a shadow outside the system by habit. The token build maps every group of tokens or names why it leaves one out, so a new group is a decision.

## Docs theme: on top of VitePress's default theme

The docs theme extends the default theme and restyles it. It does not replace it.

| Option                                                             | Example                                             | Why or why not                                                                                                                                                                                                                         |
| ------------------------------------------------------------------ | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Extend the default theme: variables, stylesheets, layout slots** | `vitepress-theme-tui`, most branded VitePress sites | Chosen. A site keeps its whole config: nav, sidebar, search, i18n, edit links. Accessibility and search come from VitePress and stay maintained there                                                                                  |
| A theme of its own                                                 | `@vue/theme`, about a hundred files                 | Full control over the markup, and no dependency on the default theme's class names. But it means owning the sidebar, the outline, the search, the mobile menus and their accessibility for good, which a lean first version should not |

The price is that the stylesheets address the default theme's class names, and its component styles are scoped, so selectors repeat a bit of structure to win. The theme therefore follows VitePress 1, and a new major version needs a pass over `src/vitepress/styles/`. The screenshot tests would show what moved.

The theme's client code ships as source, as `@vue/theme` does, so the site's own build compiles it. The base config has to be loaded by Node, so it ships compiled.

The status line and the tab numbering are real: keys are bound to the controls they are shown on, in one small module that the framework-free pages use too.

Those keys are single characters, which WCAG 2.1.4 allows only with a way to turn them off, to remap them, or to limit them to a focused control. The way here is one switch in the status line, `keys on`, that the same module wires and the browser remembers. It follows the switch pattern of the ARIA Authoring Practices, and what GitHub does with its "character keys" setting: one remembered choice that rests every single-key shortcut. The module makes the switch a condition: a key acts only on a page that has one, so a page cannot have the keys without the way out. A held key acts once, because a key that repeats would switch the theme many times a second, a flash WCAG 2.3.1 forbids. There is no site option to drop it and no remapping.

In the tab bar the brand has a box as wide as the sidebar and the tabs start where it ends, so one length places both the border of the sidebar and the left edge of the first tab, in plain CSS, with nothing measured in a script. A short brand leaves a gap before the tabs, which is accepted. An earlier form put the first tab inside that box, with its right edge on the border. It kept the tabs next to the brand, but the brand and the first tab then had to share about 17 characters, a project name such as `building-blocks` was cut, and the brand needed CSS anchor sizing to learn how wide the tab was. Now only a brand longer than the sidebar is cut, and the tabs have no limit that comes from the brand.

## Asset kit: a generator on established libraries

`scripts/generate-assets.ts` draws every file from the sprite data: SVG as strings, PNG through [resvg](https://github.com/linebender/resvg), ICO through `png-to-ico`, and text as outlines through `opentype.js`.

| Option                                                                        | Why or why not                                                                                                                                                                                         |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A generator of our own on those libraries**                                 | Chosen. The marks are sprites that must land on whole pixels at every size, which a favicon tool that scales one image cannot promise. The same code draws marks, lockups and banners from one drawing |
| Favicon generators: `@vite-pwa/assets-generator`, `favgen`, `modern-favicons` | They take one image and resize it. At 180 px a 16 x 16 sprite does not divide evenly, so pixels blur. They also do nothing for lockups and banners                                                     |
| Satori for the banners                                                        | It renders HTML to SVG and needs fonts at build time. The banner is a fixed layout of a few lines and a sprite, which is less code as SVG than as HTML                                                 |

resvg was chosen over sharp because it draws the same pixels on every platform. That is what lets the generated kit be committed and checked: `assets/` is in the repository so a change to artwork shows in a pull request as changed images, a README can show its own header, and CI fails when `assets/` is not what the sources produce.

## Fonts: from Fontsource at build time

The variable fonts and their licenses are copied from the Fontsource packages into `dist/fonts/` when the package builds, with a stylesheet that declares the `latin` and `latin-ext` subsets. No font file is kept in the repository, the lockfile pins the versions, and the package is self-contained for a project that uses it.

Depending on the Fontsource packages at runtime was the alternative. It would make every consumer resolve another package's CSS, and ship all subsets.

## Checks

- Contrast is a unit test, not a manual table: `tokens/contrast.json` lists the pairs and their bars, and the component tier's pairs follow from its names.
- Stylelint rejects a hex value, a named color and a color written with one of the functions `rgb`, `rgba`, `hsl`, `hsla`, `oklch`, `oklab`, `lab`, `lch` and `hwb` in the stylesheets. The rules are the package's `stylelint` entry, which this repository extends as every project does, so the projects lint with the rules of the version they install and need no copy of their own. They live here and not in a shared config package because they are the design system's policy and read its `tokens.css`.
- The screenshots are taken and compared in the Playwright container, on Linux, because text is drawn differently on every system. They are committed, so a visual change shows in a pull request.
- Lint and format are those of the shared template, [whatsaaaa/template](https://github.com/whatsaaaa/template): oxlint, ESLint for Vue and TypeScript, and oxfmt, with their rules from the shared config packages. Copier renders their config files from the template, and `copier update` brings its changes.
